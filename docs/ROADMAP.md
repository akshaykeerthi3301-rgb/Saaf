## Build Philosophy

1. **Each phase ships something usable.** No phase leaves the app broken. After any phase, you can demo what you've built.
2. **Infrastructure before features.** Phase 0 sets up everything so feature work later is fast and clean.
3. **Magic moment first.** The gate engine and the shortlist are built against the 233 real roles already probed from seven boards, *before* automated ingest exists. The refusal screenshot — the product's first earnable proof — is achievable at the end of Phase 2.
4. **Test as you go.** Every task ends with a verification step. `src/gates/` gets real unit tests, because it decides what a candidate is allowed to see.
5. **Progressive enhancement.** Simplest working version first, polish layered on.
6. **Build straight through.** Work through all phases in one go — no pull request between phases. For a quality pass, run Claude Code's `/review` and `/security-review`.
7. **A wrong refusal is worse than a wrong match.** It reproduces the exact injury this product exists to fix, with more authority than a portal ever had. When extraction confidence is low, let the role through rather than refusing it.
8. **Never let a failure read as a verdict.** An empty list, a zeroed audit strip, or a silent gate must never appear where the honest arithmetic belongs. A backend problem must never look like a judgement about the candidate.

## Agent Session Guide

### How to Use This Roadmap with Your Coding Agent

1. **Start a session:** Give your coding agent the "Starting a new phase" prompt below.
2. **Read selectively:** Each phase lists its Reference sections. Read only those, not the whole PRD — it is ~10,000 words and loading it entirely wastes context you need for code.
3. **Let it work:** The agent finds the first unchecked task, implements it, verifies it, and marks it `- [x]`. **One exception today: TASK-039 is unchecked but not actionable** — it needs seven elapsed days of cron runs, not code. Skip it and start at TASK-060.
4. **One session = one phase, ideally.** If you stop, resume from the last unchecked task.
5. **Build straight through:** No pull request between phases. For a quality pass — after Phase 2 and again before Phase 5 — run `/review`, and `/security-review` before launch.
6. **Need more context?** If a task references a section not listed, read just that section on demand.

### Session Tips

- **Don't read everything.** The PRD is long by design; the Reference sections tell you exactly which parts matter for the phase in hand.
- **Don't skip tasks.** Ordering resolves dependencies — there are no cross-references to chase.
- **`src/match/score.ts` is the one place to slow down.** It decides the order a candidate sees, which is now the whole product; `src/gates/extract.ts` feeds it by reading requirements out of postings. A silent regression in either causes the exact harm this product exists to prevent. Never change them without running their tests. *(`src/gates/evaluate.ts`'s verdict path is demo-only — `scripts/evaluate-fixture.ts` is its sole live caller.)*
- **Never let a backend failure render as a verdict.** Empty lists, zeroed counts and silent gates are all defects when the honest arithmetic belongs there instead.
- **Update the status line** after each task: `**Status:** X/66 tasks complete, Y discarded, Z open` and `**Current Phase:** …`.
- **No deployment until Phase 7 is done.** The founder set this explicitly on 2026-09-05. Stage C and every parity task ship together in one deploy at the end — don't deploy partway through to "check progress."
